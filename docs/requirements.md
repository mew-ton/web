# ポートフォリオサイト 要件定義

- ステータス: ドラフト
- 最終更新: 2026-10-01

## 1. コンセプト

入口は `curl mewton.jp`。ターミナルから叩くとプロフィールがテキストで返ってくる。

ブラウザで `mewton.jp` を開いた場合は、ブラウザ内で動くターミナル（WebContainer）を出すだけで、そこで同じように `curl mewton.jp` を叩いて読む。

```
$ curl mewton.jp           # 目次
$ curl mewton.jp/about     # 自己紹介・スキル・経歴
$ curl mewton.jp/works     # 作ったものの一覧
$ curl mewton.jp/works/foo # 主要作品の詳細
$ curl mewton.jp/talks     # 執筆・登壇の一覧
$ curl mewton.jp/contact   # 連絡先
```

## 2. 目的

| 優先 | 目的 | サイトに求めること |
| --- | --- | --- |
| 1 | 転職・就職活動 | 採用担当・エンジニアが短時間でスキルと実績を把握できる。ターミナルを使えない人にも代替のテキスト表示で届く（6章） |
| 2 | 個人ブランディング | 活動全体（作品・OSS・執筆・登壇・SNS）への入口になる。`curl` で叩ける入口そのものが印象に残る |
| 3 | 技術の実験場 | サイト全体（コンテンツネゴシエーション、WebContainer）が実験の場になる |

> 優先順位は仮置き。目的同士がぶつかった場合（例: 演出 vs 読みやすさ）は上位を優先する。

## 3. 想定読者

| 読者 | 主な読み方 |
| --- | --- |
| エンジニア（技術面接官、OSS 利用者など） | 自分のターミナルで `curl`、またはブラウザのターミナル |
| 採用担当者（非エンジニアを含む） | ブラウザ。ターミナルを操作しなくても代替のテキスト表示で読める |
| スクリーンリーダー利用者・検索エンジン | 代替のテキスト表示 |

## 4. 掲載する分野

- Web開発
- デザイン
- OSS・ライブラリ
- 執筆・登壇

## 5. パス構成と内容

すべてのパスで、`curl` には本文テキストを、ブラウザにはターミナルの画面を返す（7.1）。

| パス | 内容 |
| --- | --- |
| `/` | 目次。一言プロフィール、各パスの案内（叩くべきコマンドの一覧） |
| `/about` | 自己紹介、スキル、経歴 |
| `/works` | 作ったもの（Web開発・デザイン・OSS）の一覧。分野が判別できる |
| `/works/<slug>` | 主要作品のみ。背景・担当範囲・使用技術・成果 |
| `/talks` | 執筆・登壇の一覧。外部（記事・スライド・動画）へのリンク |
| `/contact` | メールアドレス・SNS へのリンク |

### 5.1 Works の扱い

- 「作ったもの」（Web開発・デザイン・OSS）は `/works`、「話したもの・書いたもの」（執筆・登壇）は `/talks` に分ける。
- 詳細（`/works/<slug>`）は主要作品のみ。それ以外は一覧の1項目（概要＋外部リンク）だけにする。
- 詳細の有無は Markdown 本文の有無だけで決める（8.2）。
- テキストでは画像を見せられないため、デザイン作品は画像を見られる外部リンク（Figma、Dribbble など）を必須にする。

### 5.2 Works 1件あたりの項目（案）

| 項目 | 必須 | 備考 |
| --- | --- | --- |
| slug | ○ | パスになる。ファイル名から決める |
| タイトル | ○ | |
| 分野 | ○ | Web開発 / デザイン / OSS（複数可） |
| 概要（1〜2文） | ○ | 一覧に表示 |
| 期間・時期 | ○ | |
| 担当範囲・役割 | △ | チーム開発の場合は必須 |
| 使用技術 | ○ | |
| 外部リンク | △ | 公開URL / GitHub / Figma など。デザイン作品は画像を見られるリンクが必須 |
| 詳細本文 | △ | 主要作品のみ。Markdown 本文として書く |

### 5.3 Talks & Writing 1件あたりの項目（案）

種別（記事 / 登壇）、タイトル、日付、媒体・イベント名、外部リンク。

### 5.4 問い合わせ

- フォームは設けない。メールアドレスと SNS（DM）へのリンクのみ。
- メールアドレスの露出方法（そのまま記載 / 簡易な難読化）は未決定。

## 6. ターミナルを使わない人への代替表示

- ブラウザ向けの HTML には、そのパスの本文テキスト（`curl` で返すものと同じ内容）をサーバー側で埋め込んでおく。
- JavaScript が動かない環境、WebContainer 非対応のブラウザ、スクリーンリーダー、検索エンジンは、この埋め込みテキストを読む。
- 対応ブラウザでは、埋め込みテキストをターミナルに置き換える。ターミナル起動中もテキストが先に見えている状態にする。
- 代替表示の中のリンクは HTML のリンクとして押せるようにする。

## 7. 技術スタック

| 層 | 採用 | 備考 |
| --- | --- | --- |
| サーバー | Nitro | リクエストに応じてテキスト / HTML を出し分ける（7.1） |
| ブラウザのターミナル | WebContainer API | ブラウザ内でシェルを動かす（7.2） |
| HTML の生成 | Nitro 単体 | UI フレームワークは使わない。ターミナルを出す1枚の HTML と代替テキストだけを組み立てる |
| コンテンツ管理 | Markdown＋YAML の併用 | 8.2 |

### 7.1 テキストと HTML の出し分け

- `Accept` ヘッダーで判定する。`text/html` を含む（＝ブラウザ）なら HTML、それ以外（`curl` の既定は `Accept: */*`）ならテキストを返す。
- User-Agent では判定しない。ブラウザ内のターミナルから送るリクエストは User-Agent を書き換えられないため、判定基準を `Accept` に一本化する。
- レスポンスに `Vary: Accept` を付け、CDN やキャッシュが HTML とテキストを取り違えないようにする。
- テキストの応答には CORS ヘッダー（`Access-Control-Allow-Origin: *`）を付ける。ブラウザ内のターミナルが別オリジン扱いでリクエストする可能性があるため（7.2 の検証で要否を確認する）。
- 出し分けがあるため、すべてを静的ファイルとして事前生成して配信する構成は取れない。サーバー（またはエッジ）で Nitro を動かす。

### 7.2 WebContainer を使うことによる制約

| 制約 | 対応方針 |
| --- | --- |
| ページのクロスオリジン分離（COOP / COEP ヘッダー）が必要 | HTML の応答すべてに付ける。外部の画像や埋め込みは使わない方針なので、これによる問題はない |
| WebContainer 内のシェルに `curl` があるか、外部へ通信できるかが未検証 | 最初に検証する。`curl` が無い場合は、同じ名前のコマンドを自前で用意して `curl mewton.jp` が動くようにする |
| 対応ブラウザが限られる（スマートフォンを含む） | 非対応環境では6章の代替表示のまま見せる |
| 起動時の読み込みが重い | 代替テキストを先に見せる（6章） |
| ブラウザ向け JavaScript のバンドル | Nitro はブラウザ向けのコードをバンドルしないため、別途ビルドして静的アセットとして配信する。COEP の制約で CDN からの読み込みは避ける |
| 利用ライセンス | 個人ポートフォリオでの利用条件を公式で確認する（要確認） |

### 7.3 ブラウザでパスを開いたときの動き

- ブラウザで `mewton.jp/works` などを直接開いた場合、ターミナルを起動して `curl mewton.jp/works` を自動で実行した状態にする。URL とターミナルに表示される内容を一致させるため。

## 8. テキスト出力

### 8.1 出力の書式

- ターミナル幅 80 桁に収まるように組む。日本語の全角文字は2桁として数える。
- 色・太字（ANSI エスケープシーケンス）を使うかどうかは未決定。使う場合、パイプやファイルへ保存したときに制御文字が混ざる問題への対処も決める。

### 8.2 コンテンツのデータ形式

| 対象 | 形式 | 構成 |
| --- | --- | --- |
| Works | Markdown＋frontmatter | 1作品＝1ファイル。メタ情報（5.2）は frontmatter、詳細の本文は Markdown 本文に書く |
| Talks & Writing | YAML | 全件を1ファイルにまとめる。外部リンクのみで本文を持たないため |
| About / Contact | 未決定 | |

- 詳細を出すかどうかは「Markdown 本文があるか」だけで決める。別途フラグを持つと本文の有無とフラグが食い違いうるため、判定元を一つにする。
- ビルド時に frontmatter / YAML を検証し、必須項目の欠落があればビルドを失敗させる。
- テキスト出力と代替表示は同じデータから生成する。

## 9. 非機能要件

| 項目 | 要件 |
| --- | --- |
| 言語 | 日本語のみ |
| 公開先 | 独自ドメイン `mewton.jp`。Nitro をサーバーまたはエッジで動かせて、レスポンスヘッダーを制御できるホスティング先 |
| スマートフォン | 代替表示で読めること。ターミナルの操作性は問わない |
| パフォーマンス | 代替テキストが WebContainer の起動を待たずに表示されること |
| アクセシビリティ | 代替表示で担保する（6章） |
| SEO / OGP | HTML に各パスのタイトル・説明・OGP 画像と、本文の代替テキストを持たせる |
