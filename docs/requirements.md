# ポートフォリオサイト 要件定義

- ステータス: ドラフト
- 最終更新: 2026-10-01

## 1. 目的

| 優先 | 目的 | サイトに求めること |
| --- | --- | --- |
| 1 | 転職・就職活動 | 採用担当・エンジニアが短時間でスキルと実績を把握できる |
| 2 | 個人ブランディング | 活動全体（作品・OSS・執筆・登壇・SNS）への入口になる |
| 3 | 技術の実験場 | 新しい技術を試せて、本体の閲覧体験を損なわない |

> 優先順位は仮置き。目的同士がぶつかった場合（例: 実験的な演出 vs 読みやすさ）は上位を優先する。

## 2. 想定読者

- 採用担当者（非エンジニアを含む）
- 現場エンジニア・デザイナー（技術面接官、OSS 利用者など）

## 3. 掲載する分野

- Web開発
- デザイン
- OSS・ライブラリ
- 執筆・登壇

## 4. ページ構成

| ページ | パス（仮） | 内容 |
| --- | --- | --- |
| トップ | `/` | 一言プロフィール、代表作のピックアップ、各ページへの導線 |
| About | `/about` | 自己紹介、スキル、経歴 |
| Works | `/works` | 作ったもの（Web開発・デザイン・OSS）の一覧。分野タグで判別できる |
| Works 詳細 | `/works/[slug]` | 主要作品のみ。背景・担当範囲・使用技術・成果 |
| Talks & Writing | `/talks` | 執筆・登壇の一覧。外部（記事・スライド・動画）へリンク |
| Contact | `/contact` またはフッター | メールアドレス・SNS へのリンクのみ |

### 4.1 Works の扱い

- 「作ったもの」（Web開発・デザイン・OSS）は Works、「話したもの・書いたもの」（執筆・登壇）は Talks & Writing に分ける。
- 詳細ページは主要作品のみ作る。それ以外は一覧のカード（概要＋外部リンク）だけにする。
- 作品ごとに「詳細ページあり／なし」を切り替えられるデータ構造にする。

### 4.2 Works 1件あたりの項目（案）

| 項目 | 必須 | 備考 |
| --- | --- | --- |
| タイトル | ○ | |
| 分野 | ○ | Web開発 / デザイン / OSS（複数可） |
| 概要（1〜2文） | ○ | カードに表示 |
| サムネイル画像 | △ | デザイン作品は必須 |
| 期間・時期 | ○ | |
| 担当範囲・役割 | ○ | チーム開発の場合 |
| 使用技術 | ○ | |
| 外部リンク | △ | 公開URL / GitHub / Figma など |
| 詳細ページ本文 | △ | 主要作品のみ |

### 4.3 Talks & Writing 1件あたりの項目（案）

種別（記事 / 登壇）、タイトル、日付、媒体・イベント名、外部リンク。

## 5. 問い合わせ

- フォームは設けない。メールアドレスと SNS（DM）へのリンクのみ。
- メールアドレスの露出方法（そのまま記載 / 簡易な難読化）は未決定。

## 6. デザイン

- ミニマル・テキスト中心。読みやすさと余白を重視する。
- デザイン作品は一覧ではサムネイル、詳細ページで画像を大きく見せる（テキスト中心の方針の中でも、デザイン実績の訴求は画像で担保する）。

## 7. 技術の実験場としての扱い

- 試したいテーマはまだ決まっていない。
- 実験は本体の読みやすさを損なわない形で後から足せる構造にする（例: `/lab` 配下に隔離する、または機能単位で有効化できるようにする）。

## 8. 非機能要件

| 項目 | 要件 |
| --- | --- |
| 言語 | 日本語のみ |
| 公開先 | 独自ドメイン（取得済み） |
| レスポンシブ | スマートフォン〜デスクトップ |
| パフォーマンス | 静的配信を基本とし、Lighthouse で高スコアを目標にする（具体値は未定） |
| アクセシビリティ | 見出し構造・代替テキスト・コントラストを担保する |
| SEO / OGP | 各ページにタイトル・説明・OGP 画像を設定する |
