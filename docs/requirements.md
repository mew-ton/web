# ポートフォリオサイト 要件定義

- ステータス: ドラフト
- 最終更新: 2026-10-01（試作の検証結果を反映）

## 1. コンセプト

入口は `curl https://mewton.jp`。ターミナルから叩くとプロフィールがテキストで返ってくる。http は使わない（7.1）。

ブラウザで `mewton.jp` を開くと、中央に `curl https://mewton.jp` のコマンドがあり、その下に同じ本文が表示されている。薄く出ている「ターミナルを開く」から、ブラウザ内で動くターミナル（WebContainer）を開き、そこでも同じように `curl` を叩いて読める（5.5）。

```
$ curl https://mewton.jp           # 目次
$ curl https://mewton.jp/about     # 自己紹介・スキル・経歴
$ curl https://mewton.jp/works     # 作ったものの一覧
$ curl https://mewton.jp/works/foo # 主要作品の詳細
$ curl https://mewton.jp/talks     # 執筆・登壇の一覧
$ curl https://mewton.jp/contact   # 連絡先
```

## 2. 目的

| 優先 | 目的 | サイトに求めること |
| --- | --- | --- |
| 1 | 技術の実験場 | サイト全体（コンテンツネゴシエーション、WebContainer）が実験の場になる |
| 2 | 転職・就職活動 | 採用担当・エンジニアが短時間でスキルと実績を把握できる。ターミナルを使えない人にも初期画面の本文で届く（6章） |
| 3 | 個人ブランディング | 活動全体（作品・OSS・執筆・登壇・SNS）への入口になる。`curl` で叩ける入口そのものが印象に残る |

> 1位は確定（2026-10-02）。2位・3位は従来の順を引き継いだ。目的同士がぶつかった場合（例: 演出 vs 読みやすさ）は上位を優先する。つまり、試したい技術や演出を読みやすさより優先してよい。ただし初期画面の本文（6章）は残す（転職目的の読者が読めなくなるため）。

## 5. パス構成と内容

すべてのパスで、`curl` には本文テキストを、ブラウザにはターミナルの画面を返す（7.1）。

| パス | 内容 |
| --- | --- |
| `/` | 目次。一言プロフィール、各パスの案内（叩くべきコマンドの一覧） |
| `/about` | 自己紹介、スキル、経歴 |
| `/works` | 作ったもの（Web開発・デザイン・OSS）の一覧。分野が判別できる |
| `/works/<slug>` | 主要作品のみ。背景・担当範囲・使用技術・成果 |
| `/talks` | 執筆・登壇の一覧。外部（記事・スライド・動画）へのリンク |
| `/contact` | メールアドレス・SNS へのリンク |

### 5.1 Works の扱い

- 「作ったもの」（Web開発・デザイン・OSS）は `/works`、「話したもの・書いたもの」（執筆・登壇）は `/talks` に分ける。
- 詳細（`/works/<slug>`）は主要作品のみ。それ以外は一覧の1項目（概要＋外部リンク）だけにする。
- 詳細の有無は Markdown 本文の有無だけで決める（8.2）。
- テキストでは画像を見せられないため、デザイン作品は画像を見られる外部リンク（Figma、Dribbble など）を必須にする。

### 5.2 Works 1件あたりの項目（案）

| 項目 | 必須 | 備考 |
| --- | --- | --- |
| slug | ○ | パスになる。ファイル名から決める |
| タイトル | ○ | |
| 分野 | ○ | Web開発 / デザイン / OSS（複数可） |
| 概要（1〜2文） | ○ | 一覧に表示 |
| 期間・時期 | ○ | |
| 担当範囲・役割 | △ | チーム開発の場合は必須 |
| 使用技術 | ○ | |
| 外部リンク | △ | 公開URL / GitHub / Figma など。デザイン作品は画像を見られるリンクが必須 |
| 詳細本文 | △ | 主要作品のみ。Markdown 本文として書く |

### 5.3 Talks & Writing 1件あたりの項目（案）

種別（記事 / 登壇）、タイトル、日付、媒体・イベント名、外部リンク。

### 5.4 問い合わせ

- フォームは設けない。メールアドレスと SNS（DM）へのリンクのみ。
- メールアドレスはそのまま記載する（難読化しない）。

## 5.5 実験場としての体験

目的の1位（2章）。`curl` の入口と WebContainer のターミナルに加えて、**ターミナル上の体験**を実験の主題にする（2026-10-02）。

### 5.5.1 初回公開の範囲

画面は2つの状態を持つ。

**初期画面**（ページを開いた直後）

- 中央に、開いたパスに対応する `curl` コマンド（例: `curl https://mewton.jp/works`）を表示する。コピーボタンを付け、自分のターミナルに貼って試せるようにする
- コマンドの下に、そのパスの本文（`curl` で返すのと同じ内容）を表示する（6章）
- 「ターミナルを開く」への導線を薄く表示する

**ターミナルを開いた状態**

1. 画面の下からターミナルのパネルが伸びてくる
2. 初期画面と同じ `curl` コマンドが**薄い文字の候補**（ゴーストテキスト）として表示されている。Tab または → で確定し、Enter で実行する。自分で別のコマンドを打てば候補は消える
3. 実行するとプロフィール（5章の本文）が表示される。少しずつ流す演出はしない（curl で叩いた場合も同じ）
4. `ls` / `cd` / `cat` などが使え、**作品のプロジェクト**ごとのフォルダがある。プロフィールはフォルダには置かず、`curl` で読む

- WebContainer はターミナルを開いたときに起動する（ページを開いただけでは起動しない）。SEO のため、初期画面は軽いサーバー生成の HTML（コマンドと本文）だけで成り立たせる。
- ターミナル用のスクリプト（WebContainer・xterm.js）も、ターミナルを開いたときに初めて読み込む。ページを開いた時点で読み込むのは、コピーボタンとパネルの開閉に必要な小さなスクリプトだけにする。
- COOP / COEP ヘッダーは、ページを開いた時点で付いている必要がある（後から付けられない）ため、引き続き HTML の応答すべてに付ける。検索エンジンによる本文の読み取りには影響しない。
- ここで足す体験は、`curl` で読める本文（5章）と初期画面の本文（6章）を壊さないこと。
- 候補の表示はブラウザ側（xterm.js の上）で行う。WebContainer 内のシェルには手を入れない。

### 5.5.2 将来の展望（初回公開には含めない）

- `cd` で作品のフォルダへ移動すると、そのプロジェクトを非同期に読み込み、ブラウザ内（WebContainer）で Node.js のサーバーを起動して動かせる。
- サーバーが起動すると、ターミナルパネル以外の残りの領域に iframe が現れ、`localhost` にアクセスできる小さなブラウザとして動く（アドレス欄にはサーバーの URL を表示する）。
- 初回公開では、この展望に向けて「作品ごとのフォルダ」という構造と、ターミナルパネル以外の領域を後から使える画面構成だけ用意しておく。
- 要調査: WebContainer で起動したサーバーのプレビューを iframe で表示するとき、このサイトの COOP / COEP と両立するか。

### 5.5.3 作品フォルダと候補（2026-10-02）

- 作品フォルダは、作品を作るときに用意する。初回公開時の中身は `README.md` のみ。
- 現時点で掲載する作品は無いため、フォルダも無い（`ls` で空の状態がありうる）。
- ターミナルの候補（薄い文字）は、ターミナルを開いた最初の1回だけ出す。

未決定（一旦保留）:

- 作品データ（8.2 の `content/works/<slug>.md`）とフォルダの `README.md` の関係（同じものにするか、生成するか、別々に書くか）。決めるまでは、同じ作品の説明が2か所に分かれて食い違うおそれがある点に注意する。

## 6. 初期画面の本文（ターミナルを使わない人への表示）

- ブラウザ向けの HTML には、そのパスの本文テキスト（`curl` で返すものと同じ内容、色なし）をサーバー側で埋め込み、初期画面でコマンドの下に表示する（5.5.1）。
- ターミナルを使わない人（採用担当者など）、JavaScript が動かない環境、WebContainer 非対応のブラウザ、スクリーンリーダー、検索エンジンは、この本文を読む。
- ターミナルを開いても本文は消さない（ターミナルはパネルとして重なるだけ）。
- 本文の中のリンクは HTML のリンクとして押せるようにする。サイト内を指す `curl` コマンドは、そのパスへのリンクにする。

## 7. 技術スタック

| 層 | 採用 | 備考 |
| --- | --- | --- |
| サーバー | Nitro | リクエストに応じてテキスト / HTML を出し分ける（7.1） |
| ブラウザのターミナル | WebContainer API | ブラウザ内でシェルを動かす（7.2） |
| HTML の生成 | Nitro 単体 | UI フレームワークは使わない。初期画面（コマンドと本文）とターミナルパネルを持つ1枚の HTML を組み立てる |
| コンテンツ管理 | Markdown＋YAML の併用 | 8.2 |

### 7.1 テキストと HTML の出し分け

- `Accept` ヘッダーで判定する。`text/html` を含む（＝ブラウザ）なら HTML、それ以外（`curl` の既定は `Accept: */*`）ならテキストを返す。
- User-Agent では判定しない。ブラウザ内のターミナルから送るリクエストは User-Agent を書き換えられないため、判定基準を `Accept` に一本化する。
- レスポンスに `Vary: Accept` を付け、CDN やキャッシュが HTML とテキストを取り違えないようにする。
- テキストの応答には CORS ヘッダー（`Access-Control-Allow-Origin: *`）を付ける。ブラウザ内のターミナルが別オリジン扱いでリクエストする可能性があるため（7.2 の検証で要否を確認する）。
- 出し分けがあるため、すべてを静的ファイルとして事前生成して配信する構成は取れない。サーバー（またはエッジ）で Nitro を動かす。
- 通信は https に限る。http のリクエストはホスティング側で https へリダイレクトする。公開プロフィールでも、経路上での改ざんを防ぐことを入口の短さより優先する。
- そのため `curl mewton.jp`（スキーム無し＝http）ではリダイレクトの応答が返るだけで本文は出ない。案内に表示する正式な叩き方は `curl https://mewton.jp` に統一する。`curl -L mewton.jp` でもリダイレクトを追って読める。
- サーバー（アプリ）ではプロトコルを判定せず、リダイレクトもしない。判定方法がランタイムごとに異なるため（7.4）。
- HTML の応答に `Strict-Transport-Security` を付け、2回目以降のブラウザのアクセスは最初から https にする。サブドメインには広げない（`includeSubDomains` は付けない）。

### 7.2 WebContainer を使うことによる制約

| 制約 | 対応方針 |
| --- | --- |
| ページのクロスオリジン分離が必要（`Cross-Origin-Opener-Policy: same-origin` と `Cross-Origin-Embedder-Policy: require-corp`。パッケージ同梱の README で確認済み） | HTML の応答すべてに付ける。外部の画像や埋め込みは使わない方針なので、これによる問題はない |
| HTTPS 必須（localhost を除く。同 README で確認済み） | サイト全体を https に限る（7.1） |
| 実行時に StackBlitz のサーバー（stackblitz.com など）に依存する | 届かない場合 `boot()` は失敗も完了もしないため、20秒で打ち切り、ターミナルを開けなかったことをパネルに表示する（初期画面の本文はそのまま） |
| 標準の `curl` はある見込み（WebContainer API のチュートリアル環境のターミナルで使えたとの報告）。ただし、このサイト上で `curl https://mewton.jp` が通るか（WebContainer 内の通信が CORS などで失敗しないか）は未検証 | 起動時に標準の `curl` で実際にこのサイトを叩き、本文が返れば標準の `curl` を、失敗すれば自前の同名コマンド（https で取得）を使う |
| 対応ブラウザが限られる（スマートフォンを含む） | 非対応環境では「ターミナルを開く」を出さないか、開けない旨を表示する。本文は初期画面で読める（6章） |
| 起動時の読み込みが重い | ページを開いた時点では起動せず、ターミナルを開いたときに起動する。本文は初期画面に最初から表示されている（6章） |
| ブラウザ向け JavaScript のバンドル | Nitro はブラウザ向けのコードをバンドルしないため、esbuild で別途ビルドして静的アセットとして配信する。COEP の制約で CDN からの読み込みは避ける |
| 利用条件 | npm パッケージ `@webcontainer/api` 自体は MIT。ただし README に「利用すると StackBlitz の利用規約に同意したことになる」とあるため、個人ポートフォリオでの利用条件は規約で確認する（要確認） |

### 7.3 ブラウザでパスを開いたときの動き

- ブラウザで `mewton.jp/works` などを直接開いた場合、初期画面の中央のコマンドと本文はそのパスのもの（`curl https://mewton.jp/works`）にする。ターミナルを開いたときの候補も同じコマンドにする（自動では実行しない。5.5.1）。URL・表示・候補を一致させるため。

### 7.4 ランタイムに依存しない作り

#### Nitro 以外を検討した結果（2026-10-02）

- バックエンドの言語を変えても、デプロイ先は実質増えない。デプロイ先を絞っているのは Nitro ではなく要件（実行時の出し分け、ヘッダー制御、https へのリダイレクト、ネームサーバーをさくらのままにする）であり、任意の言語が動くコンテナ基盤では Nitro（`node-server`）も動くため。
- 「静的ファイル＋配信側の設定で `Accept` を振り分ける」構成にすればサーバー不要の配信先（さくらのレンタルサーバーの `.htaccess` など）が増えるが、振り分けが配信先ごとの設定に依存し、ランタイムに依存しないという方針と矛盾する。さくらのレンタルサーバーは契約していないため、この構成を採る利点もない。
- 以上から Nitro を継続する。

#### 方針

Nitro を選んだのは、同じコードをどのランタイム（Node.js、Cloudflare Workers、Deno など）にもデプロイできるようにするため。curl かどうかの判定は実行時に行う必要があるので、その判定が全ランタイムで同じ結果になるようにする。

- 判定に使うのはリクエストヘッダー（`Accept`、`Host`）だけにする。どのランタイムでもそのまま届くため。
- プロトコル（http / https）をサーバーで判定しない。h3 の `getRequestProtocol` は `X-Forwarded-Proto` ヘッダーか Node.js のソケットの暗号化有無で判定するため、Node.js のソケットが無いランタイムでは https を判定できない場合がある。
- 実行時にファイルシステムを読まない。コンテンツは Nitro の server assets としてビルド時に同梱する。
- 事前生成（prerender）や Nitro のキャッシュ（`routeRules` の `cache` / `swr` / `isr`）を使わない。出し分けの結果が固定されてしまうため。
- サーバーの前に CDN やプロキシを置く場合、HTML 応答をキャッシュさせない。CDN によっては `Vary: Accept` を考慮せずにキャッシュし、curl に HTML を返してしまうため。

## 8. テキスト出力

### 8.1 出力の書式

- ターミナル幅 80 桁に収まるように組む。日本語の全角文字は2桁として数える。
- 色・太字（ANSI エスケープシーケンス）を使う。
- 既定は色あり。クエリ `?plain` を付けると色なしのプレーンテキストを返す（例: `curl https://mewton.jp/works?plain > works.txt`）。サーバーは利用者の端末が色を表示できるか判定できないため、利用者に選ばせる。
- 80 桁の桁計算ではエスケープシーケンスを幅に数えない。
- 初期画面の本文（6章）にはエスケープシーケンスを含めない（色なしの本文を使う）。ブラウザのターミナル（xterm.js）は色をそのまま表示する。

### 8.2 コンテンツのデータ形式

| 対象 | 形式 | 構成 |
| --- | --- | --- |
| Works | Markdown＋frontmatter | 1作品＝1ファイル。メタ情報（5.2）は frontmatter、詳細の本文は Markdown 本文に書く |
| Talks & Writing | YAML | 全件を1ファイルにまとめる。外部リンクのみで本文を持たないため |
| About / Contact | 未決定 | 試作では `content/profile.yaml` に仮置き |

- 詳細を出すかどうかは「Markdown 本文があるか」だけで決める。別途フラグを持つと本文の有無とフラグが食い違いうるため、判定元を一つにする。
- ビルド時に frontmatter / YAML を検証し、必須項目の欠落があればビルドを失敗させる。
- テキスト出力と初期画面の本文は同じデータから生成する。

#### DNS への影響（ドメインはさくらインターネットで取得済み）

| 候補 | DNS の変更 | 影響 |
| --- | --- | --- |
| Cloudflare Workers | ネームサーバーをさくらから Cloudflare に変更する（独自ドメインで Workers を動かすにはゾーンを Cloudflare に置く必要がある） | 登録（レジストラ）はさくらのまま。以後 `mewton.jp` の全レコードを Cloudflare で管理するため、メール用（MX・SPF・DKIM・DMARC）を含む既存レコードを漏れなく移す。DNSSEC を有効にしている場合は切り替え前に無効化する。「Always Use HTTPS」はゾーン全体の設定なので、他のサブドメインへの影響も確認する |

| Vercel / Netlify | ネームサーバーはさくらのまま。`mewton.jp` に各社指定の A レコードを追加する（要確認） | 既存レコードに影響しない |

### 9.2 Void の調査結果（2026-10-02）

npm パッケージ `void` 0.22.0（VoidZero、現 Cloudflare 傘下。MIT）に同梱のドキュメントで確認した。公式サイトにはこの環境から接続できなかった。

| 観点 | 内容 | 要件との関係 |
| --- | --- | --- |
| 実行環境 | Cloudflare Workers。自分の Cloudflare アカウントへ直接デプロイするか、Void のプラットフォーム（ホスト型の Void Cloud、またはチームで自前設置したもの）へデプロイする | ランタイムは workerd と同じで、試作の動作確認と同じ条件 |
| 対応するアプリ | Vite 8 ＋ `voidPlugin()` が前提。Void アプリ（`routes/` の Hono ベース）、メタフレームワーク（TanStack Start / React Router / SvelteKit / Nuxt / Analog / Astro）、静的サイト | **Nitro 単体（Vite なし）は対応一覧に無い**。採用するなら Void アプリへの書き換えか Nuxt 化が必要で、7.4 の「Nitro を継続」と食い違う |
| 独自ドメイン（自分の Cloudflare へ直接） | Workers の custom domain。ゾーンを自分の Cloudflare アカウントに置く必要がある | ネームサーバーの移行が必要。Cloudflare Workers と同じメールのリスク |
| 独自ドメイン（Void Cloud） | CNAME（通信用）と TXT（所有確認）を外部 DNS に置く方式 | ネームサーバーはさくらのままでよいが、**apex（`mewton.jp`）には CNAME を置けない**。さくらの DNS が apex の別名（ALIAS など）に対応していなければ使えない（要確認） |
| キャッシュ | ISR は設定したときだけ有効。キャッシュキーはパスとクエリで、`Accept` を含まない | ISR を有効にすると curl に HTML を返しうる。使うなら無効のまま（7.4 と同じ） |
| 料金・提供状況 | Void Cloud は早期アクセス段階（検索結果より）。自分の Cloudflare へ直接デプロイする場合は Workers Free の範囲で動く | Void Cloud の料金・一般提供の時期は未確認 |
| 囲い込み | 開発者自身が「Cloudflare と密に結びついている」と明言している | 「どこにでもデプロイできる」方針とは方向が逆 |

結論: 現時点では見送る。Void を使っても apex で使う場合の DNS の問題（ネームサーバー移行か、apex に CNAME を置けない）は解決せず、Nitro からの書き換えも必要になるため。

### 9.3 Vercel へのデプロイ

コードに Vercel 専用の処理は入れない（7.4）。Vercel のビルド環境では Nitro が自動で `vercel` preset を選び、`.vercel/output`（Build Output API）を出力する（`VERCEL=1` で確認済み）。`vercel.json` にはビルドコマンドだけを書く（コンテンツ検証とブラウザ向け JavaScript のビルドを必ず通すため）。

手順:

1. Vercel でこのリポジトリをインポートする（Framework Preset は自動検出のまま、Build Command は `vercel.json` の `npm run build` が使われる）
2. Node.js のバージョンは 22 系以上（`package.json` の `engines`。`scripts/check-content.ts` を Node.js の型除去で実行するため 22.18 以上が必要）
3. Vercel の管理画面で独自ドメイン `mewton.jp` を追加する
4. さくらの DNS に、Vercel が表示する apex 用の A レコードを追加する（値は管理画面の表示に従う）。`mail` / `slmail` のレコードには触れない。CAA レコードがある場合は Vercel の証明書発行元を許可する
5. 証明書の発行を待つ

本番での確認項目:

- `curl https://mewton.jp` と各パスで本文テキストが返る
- `curl -sI http://mewton.jp` が https へのリダイレクトになる
- ブラウザで開くと HTML が返り、`crossOriginIsolated` が `true` になる（COOP / COEP が Vercel の配信層で失われていない）
- `curl -s https://mewton.jp/terminal.js` が JavaScript を返す（静的ファイルが関数より先に配信される）
- 同じパスを curl とブラウザで交互に開いても取り違えない（Vercel の CDN が `Vary: Accept` を尊重する、または関数の応答をキャッシュしない）
- ターミナル冒頭の `[diag]` 行で、標準の `curl` が使えるかを確認する（7.2）
